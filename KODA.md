# KODA — Правила работы AI-агента

Этот файл содержит правила, методологии и алгоритмы для AI-агента, работающего над проектом **Albion Online Market Screen Reader**.

---

## 1. Принципы разработки на Python

### 1.1. Методология

- **PEP 8** — соблюдение стиля кодирования Python
- **DRY (Don't Repeat Yourself)** — избегание дублирования кода
- **KISS (Keep It Simple, Stupid)** — простота решений
- **SOLID** — принципы объектно-ориентированного проектирования
- **Модульность** — разделение логики на независимые сервисы и утилиты
- **Конфигурация через `.env`** — все переменные окружения выносятся в конфиг

### 1.2. Лучшие практики

#### Структура проекта

```
project_root/
├── main.py                # Точка входа
├── .env                   # Конфигурация (не в git)
├── .env.example           # Пример конфигурации
├── requirements.txt       # Зависимости
├── src/                   # Исходный код
│   ├── config.py          # Конфигурация и константы
│   ├── logging_config.py  # Централизованное логирование
│   ├── models.py          # Модели данных
│   ├── services/          # Бизнес-логика
│   └── utils/             # Утилиты
├── scripts/               # Вспомогательные скрипты
├── tests/                 # Тесты
└── logs/                  # Логи (не в git)
```

#### Именование

- Файлы и папки: `snake_case`
- Классы: `PascalCase`
- Константы: `UPPER_SNAKE_CASE`
- Приватные методы/атрибуты: `_leading_underscore`

#### Типизация

- Использовать type hints для всех функций и методов
- Использовать `dataclasses` для моделей данных
- Использовать `typing` для сложных типов

#### Обработка ошибок

- Использовать конкретные исключения вместо `except Exception`
- Логировать ошибки через централизованную систему логирования
- Предоставлять понятные сообщения об ошибках

#### Логирование

- Использовать централизованное логирование из `src/logging_config.py`
- Не использовать `print()` в production-коде
- Разные уровни логирования: DEBUG, INFO, WARNING, ERROR, CRITICAL

### 1.3. Работа с зависимостями

- Все зависимости в `requirements.txt` с указанием версий
- Новые зависимости добавлять только после обоснования
- Использовать виртуальное окружение

## 2. Алгоритм отработки запросов пользователя

### 2.1. Этапы работы

#### Шаг 1: Анализ запроса

1. Внимательно прочитать запрос пользователя
2. Выделить ключевые требования и ограничения
3. Определить затрагиваемые компоненты проекта
4. Задать уточняющие вопросы при неоднозначности

#### Шаг 2: Концепция

1. Описать общий подход к решению
2. Предложить архитектуру решения (если нужно)
3. Указать затрагиваемые файлы и их изменения
4. Получить подтверждение от пользователя (для сложных задач)

#### Шаг 3: Реализация

1. Изучить существующий код через read-only инструменты
2. Внести изменения через инструменты редактирования/создания
3. Следовать существующему стилю и паттернам проекта
4. Использовать существующие сервисы и утилиты

#### Шаг 4: Тестирование и проверка

1. Запустить тесты (если есть)
2. Проверить типизацию (mypy/pyright)
3. Запустить линтер (flake8/pylint)
4. Проверить работоспособность изменений

#### Шаг 5: Документирование

1. Обновить README.md при изменении поведения/API
2. Добавить комментарии в код при необходимости
3. Обновить KODA.md при изменении процессов

### 2.2. Правила выполнения

- **Никогда не предполагай** наличие библиотек без проверки
- **Всегда изучай** существующий код перед изменениями
- **Следуй** существующим паттернам проекта
- **Исправляй** корневую причину, а не симптомы
- **Не исправляй** несвязанные баги вне текущего запроса
- **Закрывай** запрос полностью, включая последующие шаги

## 3. Алгоритм внесения изменений

### 3.1. Порядок действий

```
1. Анализ → 2. Концепция → 3. Код → 4. Тестирование → 5. Документирование
```

### 3.2. Детальный алгоритм

#### Перед изменениями

1. Прочитать README.md и понять контекст проекта
2. Изучить затронутые файлы через read-only инструменты
3. **Изучить логи за последний час** (`logs/app.log`) — это поможет выявить ошибки и сэкономить время пользователя
4. Понять зависимости между модулями
5. Оценить влияние изменений на другие части системы

#### Внесение изменений

1. **Сначала код** — вносим изменения через инструменты:
   - `read_file` для изучения файлов
   - `edit_file` для правок
   - `create_new_file` для новых файлов

2. **Затем тестирование**:
   - Запуск тестов: `python -m pytest tests/` (если есть)
   - Проверка типов: `mypy src/`
   - Линтинг: `flake8 src/`
   - Ручная проверка работоспособности

3. **Потом документирование**:
   - Обновление README.md при изменении API/поведения
   - Добавление комментариев в код
   - Обновление CHANGELOG.md (если есть)

### 3.3. Правила редактирования

- Показывать только изменённые участки кода
- Использовать ленивые комментарии для пропуска неизменённого кода
- Соблюдать точный отступ (tabs/spaces) как в оригинале
- Не менять несвязанный код без необходимости
- Использовать `replaceAll` только при явном запросе на замену всех вхождений

### 3.4. Проверка изменений

Перед завершением работы:

1. [ ] Запустить тесты
2. [ ] Проверить типизацию
3. [ ] Проверить линтинг
4. [ ] Убедиться, что нет лишних изменений
5. [ ] Обновить документацию при необходимости

## 4. Алгоритм работы с Git

### 4.0. Обязательный порядок действий

> **ВАЖНО:** Git-процесс обязателен для ВСЕХ изменений в коде. Исключений нет.

```
1. Внести изменения → 2. Протестировать → 3. Задокументировать → 4. Закоммитить (по завершении задачи) → 5. (По запросу) Пуш
```

**Правило:** Коммит выполняется **только после полного завершения задачи** (код + тесты + документация).

### 4.1. Оптимизация команд (KISS)

> **Цель:** Сократить количество запросов к терминалу, уменьшить время и стоимость работ.

#### Объединение команд

| Операция                     | Оптимизированная команда (PowerShell)                                |
| ---------------------------- | -------------------------------------------------------------------- |
| Git add + commit             | `git add .; git commit -m "тип: описание"`                           |
| Проверка синтаксиса + импорт | `python -m py_compile file.py; python -c "import file; print('OK')"` |
| Тесты                        | `python -m pytest tests/ -v --tb=short` (1 запуск перед коммитом)    |

#### Синтаксис PowerShell (обязательно)

> **ВАЖНО:** Все терминальные команды должны использовать синтаксис **PowerShell**, не bash!

| Операция            | ❌ Bash (НЕ использовать)          | ✅ PowerShell (правильно)                             |
| ------------------- | ---------------------------------- | ----------------------------------------------------- |
| Цепочка команд      | `cmd1 && cmd2`                     | `cmd1; cmd2`                                          |
| Git add + commit    | `git add . && git commit -m "..."` | `git add .; git commit -m "..."`                      |
| Проверка успеха     | `cmd && echo "OK"`                 | `cmd; if ($?) { Write-Host "OK" }`                    |
| Условное выполнение | `cmd1 && cmd2 \|\| echo "error"`   | `cmd1; if ($?) { cmd2 } else { Write-Error "error" }` |

#### Что НЕ оптимизируется (требования процесса)

| Процесс                          | Причина                |
| -------------------------------- | ---------------------- |
| Подтверждение пуша пользователем | Требование п. 4.4      |
| Тесты перед коммитом             | Требование п. 5.1      |
| Изучение логов перед изменениями | Требование п. 3.2, 5.0 |

### 4.2. Ветвление (отменено)

> **ПРИМЕЧАНИЕ:** Ветвление отменено для упрощения процесса. Все коммиты делаются напрямую в **master**.

**Обоснование:**

- Один разработчик (AI-агент) — конфликтов не возникает
- 1 задача = 1 коммит — история чистая и понятная
- Меньше команд → ниже стоимость работ → быстрее результат

**Если потребуется изоляция задачи:**

- Создать ветку по явному запросу пользователя
- После завершения — запросить подтверждение на слияние

### 4.3. Внесение изменений

1. Внести изменения через инструменты редактирования
2. Проверить работоспособность (тесты, линтер, типизация)
3. **Задокументировать изменения** (обновить README.md, комментарии в коде при необходимости)
4. Закоммитить:
   ```bash
   git add . && git commit -m "тип: описание"
   ```

### 4.4. Коммит

1. Написать осмысленный коммит-месседж:

   ```bash
   git commit -m "тип: краткое описание"
   ```

   **Формат коммит-месседжа (Conventional Commits):**

   ```
   feat: добавление новой функции
   fix: исправление бага
   docs: обновление документации
   style: исправление стиля кода (без изменения логики)
   refactor: рефакторинг кода
   test: добавление или исправление тестов
   chore: обновление зависимостей, сборка, утилиты
   ```

   **Примеры:**

   ```
   feat: добавить валидацию входных данных в ImageAnalysisService
   fix: исправить ошибку парсинга цен в CSV-файле
   docs: обновить README.md с новыми примерами использования
   ```

2. **1 задача = 1 коммит** — все изменения по задаче в одном коммите

### 4.5. Пуш в репозиторий

> **⚠️ ВАЖНО:** Пуш выполняется **ТОЛЬКО после явного подтверждения пользователем**.

1. **После завершения коммита(ов)**:
   - Остановиться и **не выполнять пуш автоматически**
   - Сообщить пользователю о готовности к пушу
   - Предоставить краткую сводку (файлы, тесты, коммиты)
   - **Ожидать явного подтверждения** (например, "выполняй пуш", "push", "ok")

2. **После получения подтверждения от пользователя**:

   ```bash
   git push origin master
   ```

3. **Если пуш не подтверждён**:
   - Коммиты остаются локально
   - Перейти к следующей задаче или ожидать инструкций

## 6. Особые правила для проекта

### 6.1. Критерии выполнения задачи

- **Основной критерий**: программа запускается без ошибок
- **Дополнительный критерий**: в коде нет явных синтаксических ошибок
- Тестирование и код-ревью проводит пользователь
- Не требуется CI/CD проверки или внешние проверки

### 6.2. Управление зависимостями

- Понижать версии пакетков только по явному запросу пользователя
- Добавлять новые внешние библиотеки только по явному запросу пользователя
- Все зависимости фиксировать в `requirements.txt` с указанием версий

### 6.3. Рефакторинг и улучшения

- Проводить рефакторинг только в рамках устранения ошибки или по явному запросу
- Не проводить самостоятельные мероприятия по улучшению кода без запроса
- Не менять архитектуру без явного подтверждения пользователя

### 6.4. Работа с OCR и компьютерным зрением

- Использовать централизованный конфиг для путей к Tesseract
- Логировать распознанный текст в DEBUG-режиме
- Сохранять отладочные изображения с зонами при DEBUG_MODE=true

### 6.5. Обработка данных

- Все пути использовать через `pathlib.Path`
- Использовать централизованное логирование
- Обрабатывать ошибки файловой системы gracefully
- Не хранить секреты в коде

### 6.6. GUI-инструменты

- Использовать `readchar` для консольного меню
- Использовать `opencv` для визуализации зон
- Обеспечить корректное закрытие окон (q, Esc)

### 6.7. Горячие клавиши

- Использовать `keyboard` для глобального перехвата
- Обрабатывать конфликты с системными хоткеями
- Давать пользователю возможность перенастроить
